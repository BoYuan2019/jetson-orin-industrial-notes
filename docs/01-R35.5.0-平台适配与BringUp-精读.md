# R35.5.0 平台适配与 Bring-Up 精读（AGX Orin Industrial + 自研无 EEPROM 载板）

- 文档来源：NVIDIA Jetson Linux Developer Guide **R35.5.0** → *Jetson AGX Orin Platform Adaptation and Bring-Up*
  https://docs.nvidia.com/jetson/archives/r35.5.0/DeveloperGuide/HR/JetsonModuleAdaptationAndBringUp/JetsonAgxOrinSeries.html
- 阅读日期：2026-11-24
- 事实等级：本文所有 `[官方]` 条目均出自上述页面；`[待实测]` 表示需在本项目硬件上验证后才能写入结论
- 硬件前提：模组 Jetson AGX Orin Industrial 64GB（P3701-0008），载板自研且**无 EEPROM**

## 目标

1. 把官方 Bring-Up 章节压成一份可执行的适配清单，明确"换载板到底要改哪几处"。
2. 标出对**无 EEPROM 自研载板**影响最大的三个点（MB2 EEPROM、ODMDATA/UPHY、board.conf 覆盖关系）。
3. 区分"必须改"与"按需改"，避免一上来大改设备树。

## 该页覆盖的章节（速查）

| 章节 | 与本项目相关性 |
|---|---|
| Board Configuration / Board Naming | 高：必须起自己的 board 名 |

| Flashing the Build Image / Optional Env Vars | **最高：board.conf 覆盖机制** |

## 核心结论（先看这五条）

1. `[官方]` 换载板必须同时改 **kernel DT、MB1 配置、MB2 配置、ODM data、flashing 配置**，缺一项都可能起不来。
2. `[官方]` 无载板 EEPROM 时，必须在 `Linux_for_Tegra/bootloader/tegra234-mb2-bct-common.dtsi` 把 `cvb_eeprom_read_size` 从 `<0x100>` 改为 `<0x0>`；官方在 Flashing 节还专门提示："Users might encounter flashing/booting issues on a custom carrier board without EEPROM if the required MB2 BCT changes are not made."
3. `[官方]` **若载板不用 MGBE（10G 以太网），必须把 ODMDATA 里的 `gbe-uphy-config` 从 22 改成 0 或 1，否则板子不会启动**。这是自研载板最容易被忽略的一条。
4. `[官方]` board.conf 里的变量必须写在 `source "${LDK_DIR}/p3701.conf.common";` **之后**，否则不生效。
5. `[官方]` UEFI 优先使用 rootfs 中 `/boot/extlinux/extlinux.conf` 指定的 Image 与 dtb，而不是刷进去的分区里的——排查"我明明刷了新 dtb 却没生效"时先看这里。

## 1. Board Configuration / Board Naming `[官方]`

- 开发套件 = P3701 SOM + P3737 载板，整体编号 P3730。SOM 与载板**各有 EEPROM** 存 board ID。
- 官方要求：使用非 P3737 载板前，必须改 kernel device tree、MB1 配置、MB2 配置、ODM data、flashing 配置。
- board 命名规则：小写字母+数字，可含 `-` `_`，不能有空格；示例 `p3730-0000-devkit`、`devboard`。同时需要 `<vendor>` 命名。
- 明确禁止：**不要直接改 NVIDIA devkit 的代码而不换 board 名**，否则无法区分源码支持哪个板子。

本项目建议命名 `[待实测]`：

```
<board>  = <你的公司缩写>-orin-industrial   # 例：acme-orin-industrial
<vendor> = <你的公司缩写>                    # 例：acme
```

## 2. Placeholders `[官方]`

- `<root>` 支持的取值**只有 `emmc`**。这意味着该页的适配示例只覆盖 eMMC 作为 rootfs 的情形；NVMe 作 rootfs 要走 Flashing Support 里的 initrd 流程。
- `<version>`：NVIDIA 参考板文件带版本号（如 a00），客户平台可省略。

## 3. Root Filesystem Configuration `[官方]`

- `nv.sh` / `nvfb.sh`、Xorg 配置、nvpmodel 时钟频率等平台相关配置需要落到 rootfs 里，来源是 `Linux_for_Tegra/nv_tegra/`。
- 官方示例 rootfs（Ubuntu sample）由 `apply_binaries.sh` 自动应用这些定制。**自制的 rootfs 必须自己处理这一层**，否则 nvpmodel 等会异常 `[官方]`。

## 4. MB1：BCT 位置与 pinmux `[官方]`

- MB1 启动配置表在 `<l4t_top>/bootloader/t186ref/BCT`（注意：R36.x 改为 `bootloader/generic/BCT`，**版本不同路径不同**）。
- pinmux 生成流程：
  1. Download Center 搜 "Orin Series Pinmux"，下载 `jetson_agx_orin_pinmux_config_template.xlsm`，**选与 SOM 匹配的版本**，启用宏
  2. 按原理图填 `Pin Direction` / `Req Initial State` / `3.3V Tolerance`
  3. 点 **Generate DT File** → 得到 `pinmux.dtsi`、`gpio.dtsi`、`padvoltage.dtsi`
  4. 放置：`pinmux.dtsi` → `<l4t_top>/bootloader/t186ref/BCT/`；`gpio.dtsi` → `<l4t_top>/bootloader/`；`padvoltage.dtsi` **不需要拷贝**
  5. 在 board.conf 中把这两个文件名指过去
- 注意点：`3.3V Tolerance Enable` 打开会让该 pin 变成 open-drain；要用作纯 GPIO 时必须关闭（对应寄存器 E_IO_HV 位）。

### GPIO 编号计算 `[官方]`

```
pin_number = base + port_offset + pin_offset
```

- `base`：`tegra234-gpio` = 348，`tegra234-gpio-aon` = 316（取自 `dmesg | grep gpiochip`）
- `port_offset`：PORT_A=0、B=8、C=9、D=17、E=21、F=29、G=35、H=43、I=51、J=58、K=64、L=72、M=76、N=84、P=92、Q=100、R=108、X=114、Y=122、Z=130、AC=138、AD=146、AE=150、AF=152、AG=156；AON 侧 AA=0、BB=8、CC=12、DD=20、EE=23、GG=31
- 例：SOC_GPIO08 = GPIO3_PB.00 → 348 + 8 + 0 = **356**
- 也可直接查 debugfs：`cat /sys/kernel/debug/gpio | grep PB.00` → `gpio-356 (PB.00)`

## 5. MB2：无 EEPROM 处理（本项目最关键） `[官方]`

> EEPROM is an optional component for a customized carrier board. When the carrier board is designed without an EEPROM, in the `Linux_for_Tegra/bootloader/tegra234-mb2-bct-common.dtsi` (the MB2 BCT file), make the following modification:
> ```
> - cvb_eeprom_read_size = <0x100>
> + cvb_eeprom_read_size = <0x0>
> ```

操作 `[待实测]`：

```bash
cd Linux_for_Tegra
f=bootloader/tegra234-mb2-bct-common.dtsi
cp -a "$f" "$f.orig"
grep -n cvb_eeprom_read_size "$f"          # 确认现状为 <0x100>
sed -i 's/cvb_eeprom_read_size = <0x100>/cvb_eeprom_read_size = <0x0>/' "$f"
grep -n cvb_eeprom_read_size "$f"          # 确认已改为 <0x0>
```

失败表现（`[论坛]`，需本机复现确认）：串口停在 MB2 阶段，无法进入 UEFI/内核。

## 6. 动态改 pinmux（调试用） `[官方]`

- JetPack 5.0.2 GA 起可用 GPIO sysfs / devmem 动态改，不必重刷。
- 方法：查 TRM 得 padctl 基址与 offset（如 PADCTL_A0 = 0x02430000，SOC_GPIO37 offset 0x80 → 0x02430080），`sudo apt-get install busybox` 后用 `busybox devmem <addr>` 读、`busybox devmem <addr> w <val>` 写。
- 设为 GPIO：Bit10=0；输出 Bit4=0/Bit6=0；输入 Bit4=1/Bit6=1。
- 局限 `[官方]`：不能用 pinctrl API 改 pinmux（upstream GPIO 驱动尚不支持）。
- 40-pin header 上的 pin 可用 Jetson-IO + jetson-gpio 动态生成 DTBO，重启生效。

## 7. Porting the Linux Kernel（设备树） `[官方]`

- 前提假设：P3701 SOM 的 eMMC/PMIC/DDR 走线未变，改动集中在载板侧外设。
- 源码位置：`<top>/hardware/nvidia/platform/t23x/`、`<top>/hardware/nvidia/soc/t23x`
- 官方示例的最终 dtb 是 `tegra234-p3701-0000-p3737-0000.dtb`（**开发版 SKU P3701-0000**；工业版 P3701-0008 对应的 dtb 名请看 `jetson-agx-orin-devkit-industrial.conf` 的 `DTB_FILE`）`[待实测]`
- 常见改动位置：

| 改动类型 | 位置 |
|---|---|
| 电源树 | `tegra234-p3701-power-tree.dtsi`、`tegra234-power-tree-p3701-0000-p3737-0000.dtsi` |
| 显示 | Display Configuration and Bring-Up 章 |
| ODM data 相关功能 | `tegra234-p3737-overlay-ufs.dts`、`-overlay-pcie.dts` 等 overlay |
| SoC 控制器启停 | `soc/t23x/kernel-dts/tegra234-soc/` |

- 官方建议：**基于 3737 的 dts 复制一份并改成自己的 board 名**；改完要确认没有其它 dts/dtsi 覆盖你的改动。
- 验证改动是否生效：`dtc -I dtb -O dts <your>.dtb > out.dts` 后人工核对。

## 8. UPHY Lane 与 ODMDATA（不启动的头号原因） `[官方]`

三个 UPHY 实例：HSIO（UPHY0）、NVHS（UPHY1）、GBE（UPHY2），lane 在 PCIe/USB/UFS/MGBE 之间共享。

关键配置项：

| 选项 | 含义 |
|---|---|
| `hsio-uphy-config-0` | lane0=USB3.2 P0，lane1/2=USB3.2 P1/P2，lane3=PCIe x1 C1，lane4=PCIe x4 C4 |
| `hsio-uphy-config-16` | lane0=PCIe x1 C0，其余同上 |
| `nvhs-uphy-config-0` / `-1` | C5 作 RP / EP（**刷机时固定，运行期不可切换**） |
| `gbe-uphy-config-22` | lane0-7 = PCIe x8 C7（RP）；**这是 devkit 默认值** |
| `gbe-uphy-config-0` / `-1` | C7 作 EP + MGBE C0；不用 MGBE 时选这两个之一 |

devkit 默认 ODMDATA `[官方原文]`：

```bash
ODMDATA="gbe-uphy-config-22,nvhs-uphy-config-0,hsio-uphy-config-0,gbe0-enable-10g,hsstp-lane-map-3";
```

**官方重要提示（原文）**：*You must change gbe-uphy-config from 22 to 0 or 1 if your CVB is not using MGBE. The board will not boot without this required change.*

不用 MGBE 的典型配置 `[官方原文]`：

```bash
ODMDATA="gbe-uphy-config-0,hsstp-lane-map-3,hsio-uphy-config-16,nvhs-uphy-config-0";
```

其它 ODMDATA 规则 `[官方]`：

- `gbe0-enable-10g` 存在但 GbE0 控制器未启用 → **BPMP-FW 触发致命错误，系统不启动**
- ODMDATA 寄存器布局：bit31:26 HSIO 配置号、25:23 NVHS 配置号、22:18 GBE 配置号、17:14 GbE3..0 模式（0=5G,1=10G）
- 运行期核对：`sudo cat /sys/kernel/debug/bpmp/debug/uphy/config`（例：`0x00584000`）
- ODMDATA 默认值在 `p3701.conf.common`，可在顶层 flash 配置里覆盖

本项目待决策项 `[待实测]`：

- [ ] 载板是否有 MGBE（10G）PHY？无 → `gbe-uphy-config` 必须改 0 或 1
- [ ] 是否用 PCIe C7 x8（雷达数据链路）？用 → 需重新分配 UPHY lane
- [ ] 是否需要 C5 做 Endpoint（例如接主机）？

## 9. PCIe `[官方]`

- Orin SoC 有 11 个 PCIe 控制器，不能同时全开：C0 x1、C1 x1、C4 up to x4、C5 up to x8（dual）、C7 up to x8（dual），均 Gen4。
- C5/C7 的 RP/EP 模式**在刷机时固定**。
- 客户 CVB 启用 PCIe 的步骤：选 UPHY 配置 → 改 ODMDATA → 配 `PEX_L*_RST_N` / `PEX_L*_CLKREQ_N` pinmux（RP：RST=SFIO 输出、CLKREQ=SFIO 双向，均开 3.3V tolerance；EP：RST=GPIO 输入）→ 使能对应 pcie 节点 → 加 `phys`/`phy-names`（pipe2uphy 节点在 `tegra234-soc-pcie.dtsi`）→ EP 模式还要 `reset-gpios`。
- 供电：可用 `vpcie3v3-supply` / `vpcie12v-supply` 注册稳压器，LTSSM 前使能。
- 控制器 DT 节点：C0 `pcie@14180000`、C1 `14100000`、C4 `14160000`、C5 `141a0000`、C7 `141e0000`（EP 用 `pcie_ep@...`）。
- 链路起不来的排查：加 `nvidia,disable-power-down` 后 `lspci` 应能看到 Root Port；再查 PERST#/CLKREQ#/REFCLK/Tx-Rx 走线、板级 mux、slot 供电 GPIO；软件侧看 `lspci -vvv` 的 `LnkSta` DLActive、PADCTL_PEX_* 寄存器、`PCIE_RP_APPL_DEBUG_0`；最后降 Gen1/x1 试链路。

## 10. USB `[官方]`

- P3737 验证的是 3 个 USB3.2 口（`hsio-uphy-config-0`）。UPHY lane 与 PCIe/UFS 共享，自研板要自己核对。
- USB2 走 UTMI pad（D+/D-），USB3 走 UPHY lane（SSTX/SSRX）。
- DT 结构：`xusb_padctl`（pads/ports 子节点，命名 `<type>-<port_number>`）、`tegra_xhci`（phys/phy-names/nvidia,xusb-padctl）、OTG 还需要 `xudc` 与 `ucsi_ccg`（Cypress Type-C 控制器）节点。
- 关键属性：`mode`(host/peripheral/OTG)、`nvidia,usb2-companion`、`nvidia,oc-pin`、`vbus-supply`、`nvidia,usb3-gen1-only`。
- 若载板用 GPIO 做 ID/VBUS_DETECT，用 `gpio-usb-b-connector` 连接器节点（`id-gpios`、`vbus-gpios`、`cable-connected-on-boot`）。

## 11. 以太网 `[官方]`

- 10G PHY：`nvidia,phy-iface-mode`（0=XFI 10G、1=XFI 5G、2=USXGMII 10G、3=USXGMII 5G）、`nvidia,uphy-gbe-mode`（1=10G、0=5G）、`nvidia,phy-reset-gpio`、`nvidia,phy-rst-pdelay-msec`、`nvidia,phy-rst-duration-usec`，mdio 节点用 `nvidia,eqos-mdio`。
- 交换机：固定链路 `fixed-link { speed=<10000>; full-duplex; }`，且要求**交换机在 Orin 启动前已上电并配好端口**。
- RGMII 1G PHY：`phy-mode = "rgmii-id"`、`phy-handle`、PHY reset GPIO、MDIO 地址默认 1，另有 Tx/Rx/MDC-MDIO/RST-IRQ 的 pinmux 明细。

## 12. Flashing 与 board.conf 覆盖机制 `[官方]`

- 刷机用你自己的 board 名，脚本读 `<board>.conf`。
- `flash.sh` 会根据 EEPROM 与命令行参数推导一批环境变量；要覆盖就在 board.conf 里显式赋值。
- **关键规则（原文）**：*The parameters must be added under the reference to the `<xxx>.conf.common` file to be reflected in the flashed image.*

官方示例：

```bash
source "${LDK_DIR}/p3701.conf.common";

PINMUX_CONFIG="tegra234-mb1-bct-pinmux-p3701-0000.dtsi";
BPFDTB_FILE=tegra234-bpmp-3701-0000-3737-0000.dtb;
DTB_FILE=tegra234-p3701-0000-p3737-0000.dtb;
TBCDTB_FILE=tegra234-p3701-0000-p3737-0000.dtb;
EMMC_BCT=tegra234-p3701-0000-p3737-0000-TE990M-sdram.dts;
MISC_CONFIG=tegra234-mb1-bct-misc-p3701-0000.dts;

# 然后
sudo ./flash.sh <board> mmcblk0p1
```

可覆盖的变量（官方清单，节选）：`BCTFILE`、`BOARDID`、`BOARDREV`、`BOARDSKU`、`BOOTLOADER`、`CFGFILE`、`CMDLINE`、`DTBFILE`、`EMMCSIZE`、`KERNEL_IMAGE`、`ODMDATA`、`ROOTFSSIZE`、`ROOTFS_DIR`、`FAB`、`PINMUX_CONFIG`、`BPFDTB_FILE`、`TBCDTB_FILE`、`EMMC_BCT`、`MISC_CONFIG`。

### UEFI 与 extlinux.conf `[官方]`

> UEFI picks the kernel Image and dtb from the rootfs path mentioned in the `/boot/extlinux/extlinux.conf` file. If you mentioned an image and dtb in this file, these items will be given precedence.

即：改了 dtb 后如果 `extlinux.conf` 里写死了别的 dtb 路径，刷机不会改变实际加载的 dtb。排查时先 `cat /boot/extlinux/extlinux.conf`。

## 13. eMMC 相关（量产前再看） `[官方]`

- **EUDA（增强用户数据区）**：`mmc enh_area set -y <start KiB> <length KiB> /dev/mmcblk0`，把部分区域配成 SLC 提升重负载寿命。
  - **不可逆**：启用后容量减少，且分区表需改，**之后无法再刷机**。
  - 必须按 eMMC 厂商指引操作。
- 健康度：`mmc_utils` 读 EXT_CSD；或看 debugfs `/sys/kernel/debug/mmc0/mmc0:0001/{dhs_type_a,dhs_type_b,eol_status}`。
- 数据保持：断电 6 个月以上可能丢数据/损坏。

## 结论

- `[官方]` 换载板的五类改动（DT / MB1 / MB2 / ODM data / flashing conf）是硬性要求；无 EEPROM 需 `cvb_eeprom_read_size=<0x0>`；不用 MGBE 必须改 `gbe-uphy-config`，否则不启动；board.conf 变量须在 `source p3701.conf.common` 之后；UEFI 以 `extlinux.conf` 为准。
- `[推断]` 本项目最可能的失败点是 ODMDATA 与 UPHY lane 分配（雷达数据链路要占 PCIe），其次是 pinmux 路径放错到 `generic/BCT`（R35.5.0 应放 `t186ref/BCT`）。
- `[待实测]` 全部具体值：dtb 文件名、ODMDATA 最终串、pinmux 内容、PCIe 控制器选择、以太网形态。

## 踩坑与排查（预置）

| 现象 | 优先怀疑 | 检查 |
|---|---|---|
| 串口停在 MB2 之前 | EEPROM 读取未关闭 | `grep cvb_eeprom_read_size bootloader/tegra234-mb2-bct-common.dtsi` |
| 完全不启动、无 UEFI | ODMDATA 与硬件不符（尤其 `gbe-uphy-config-22`） | 改 0/1；查 `gbe0-enable-10g` |
| pinmux 修改无效 | 放错目录 / board.conf 未指向 | 应在 `bootloader/t186ref/BCT/`；检查 `PINMUX_CONFIG` |
| board.conf 改了不生效 | 变量写在 `source .conf.common` 之前 | 调整位置 |
| 刷了新 dtb 但行为没变 | `extlinux.conf` 指定了别的 dtb | `cat /boot/extlinux/extlinux.conf` |
| PCIe 链路不 up | lane/模式/PERST 配错 | 加 `nvidia,disable-power-down` → `lspci`；查 PADCTL 寄存器 |
